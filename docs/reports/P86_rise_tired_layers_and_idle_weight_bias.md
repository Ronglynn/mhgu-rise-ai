# P86 · Rise 疲惫时抽选层到底变了什么 + 「疲惫态偏向待机权重」方案评估

2026-11-15 22:20 · 用户两问的只读复核。无实机、未编译、未改插件/源码/部署/mods/load_order，GitHub 远端零操作。

## 1 · Rise 侧疲惫是什么情况：**不是抽选时间变长**

### 1.1 四层分解（按证据等级）

| 层 | 疲惫时发生什么 | 证据 |
| --- | --- | --- |
| **状态层** | `_IsTired` 持续布尔 + `_tiredSec` / `_hyakuryuTiredSec` + `_AddTiredTime`（RSZ 中 60 处动态累加）；78 个 `stamina_data` 中 61/78 有非零静态时长，30~120 秒、12 种值 | 静态实证 [B]（P32 §4、P80 §(c)）；GU 侧「疲惫是瞬时事件、无持续状态字」是 GU 特有，不能反推 Rise |
| **抽选层（换池）** | 由「状态 × 距离档」索引到 `tiredRange1..5` 五张池；**候选变少（平均 3 个 vs 怒/常 3.4~3.6）、熵降低（1.2984 vs 1.6740 / 1.6669）、首项权重 55~72%（怒/常 43~46%）**；`_TransitionRate` 率和恒 100 ⇒ **每次抽选仍命中一个动作**，只是更常落到同一张表 | 555 池全量 parseOK（P81/P82）；形状 `rise_15pool_shapes_555.json`、`rise_band_shapes.json` |
| **动作层（变慢）** | `_motRate` 0.8~0.98（60/78 怪非 1.0、7 种值）⇒ 动作播放速度下降（拉长 `dS`）；逐动作 `_tiredMotSpeedLowerLimitValue`（3 个 `action_param_data` 中仅 16/16/10 个显式 1.0，其余 -1.0） | 字段名与数值 [B]；作用语义无 Rise 反汇编/实机 [C] |
| **引擎 / 动画层（发呆）** | 流口水、喘气、动作后发呆或滑倒、倒地硬直、进食恢复、陷阱/闪光效力上升；公开攻略层可观测 [I] | 本项目静态资产**无法定量**：`action/combo/motion/message/actiontune` 442 条清单 437 条 0 覆盖；12 Hub、15 池、107 个 RSZ JSON 搜 `tired/drool/rest/fatigue/待机/喘` **0 命中**（除文件名）；P32:201 全部 Rise 结论无实机/反汇编 |

### 1.2 「抽选时间变长」有没有字段支持 —— 没有

- `EnemyThinkTimerData._Timer` 取值 0/3/5/…/300 秒（17 档），是**思考 / 重复抑制计时器**（配 `ConditionInfo._CheckPrevTableInfoList`、`EnemyThinkCounterData`），**P32:120 明确「不是疲惫时长，勿混用」**；`rise_ai_rules.json` `explicit_cooldown_field_found=false`。
- 抽选时机由 `ThinkCondition._IsActionEnd` 门控（动作内不重抽）；12 Hub 共 44 个 TC 中每文件恰 1 True、15 池内 TC 全 False（P32 §L3）。**没有任何「疲惫时把 Think 计时器调长」的字段或绑定证据**；P32:202 明确「Timer/Counter 与具体 ConditionInfo 的绑定、因果仍是推断」。
- ⇒ 准确说法：**Rise 疲惫 = 换一批更单一的候选 + 状态持续 + 动作变慢 + 引擎层插入待机/发呆；不是「抽选间隔变长」**。玩家感觉「两招之间久」，主要来自动作变慢和发呆，不是抽选器变慢。
- 本项目 v2 复刻的只有第二层的**权重形状**（表号集合无法复刻，GU 只有一张 `*_cmdtbl`）；第三、四层在 GU 引擎层，正是 P85 判定「没有输出窗口」的根因。

## 2 · 用户方案：疲惫态提高「待机」抽中权重，变相拉长窗口

### 2.1 这条思路确实比插间隔干净

它全在**抽选层内**：不新增 hook、不写游戏内存、不动提交时序、不碰 `0xAFF40`、不按 action_id 硬编码 ⇒ 四条纪律一条都不破。且项目已有 137 怪全量离线资料 `out/tired_struct_bias.json`（源 `out/emc_offline/weighted.tsv`，P47/P72）：

| 项 | 值 |
| --- | --- |
| 含空签名 case（`sig==FNV0`，case body 内无 `op0x14` 排队动作）的怪 | **130 / 137** |
| 空签名 case 权重占全表 | **22.3%**（564,822 / 2,532,200） |
| 按怪分布 | min 0 / p25 13.4% / **p50 22.4%** / p75 37.3% / max 100%；`<10%` 11 怪、`10-25%` 60、`25-50%` 43、`>=50%` 16 |
| 样本 | 雌火龙 22.3%、轰龙 11.9%、斩龙 15.4%、铠龙 15.9%；`cEmpty` 中位 86 / 最大 620 |

`weighted.md:22-24` 把「空签名 = 不排队动作」解释为**原生待机 / Think 间隙**（仅推断，无实机验证）。v36 实机曾记 `empt=323/551=58.6%`（旧口径，含 `mode==0` 副轨语义混用，不可直接当当前命中率），说明游戏原生确实会大量抽到这类 case。

### 2.2 成品 v2 现在的机制（决定改动点）

- `h_matcher` 在游戏算出 `ret` 后扫描 case，`rise_weight_pick()` 把合格 case 按 Rise 形状重新加权，**通过改写 `ret` 让 matcher 落到插件选中的 case**（`lib.rs:1566+`、`:2160-2185`）。⇒ 插件**有能力主动把抽选结果导向任意 case**，包括空签名 case。
- 但候选筛选是 `cs[k].sig != FNV0 && prev_hit_d(...) == 0`（`lib.rs:1575`）；外层命中 `sig_sel == FNV0` 时直接 `return r` 透传（`lib.rs:2134`），否决重抽路径也逐处排除 FNV0（`:2207/:2226/:2235`）。设计注释 v37：「空签名池仍直接透传（不是动作选择池）」。
- ⇒ **现状**：游戏原生抽中空签名 case 时插件不干预（待机保留）；游戏抽中非空签名 case 时，W1/W2/W4 只会把它改成另一个非空签名 case。插件从来没有「主动提高待机率」这条路。
- **理论推论（未实证）**：P70 疲惫窗动作密度 10.5→12.4（+18%）可能正是 W1 疲惫低熵形状 `[60,20,14,6]` 把抽选压到 top-1 非空签名 case 的结果；那么在疲惫态把一部分权重导向 FNV0，方向相反，理论上应降低动作密度。这条推论需要实机检验，不能当结论。

### 2.3 三个未闭环假设（成败全在这里）

1. **空签名 ≠ 已证实的待机**。`weighted.md` 是解释性推断；它也可能只是「条件占位 / 无动作分支」，选中后游戏可能原地发呆（v21i 把攻击换成 `id=3` 待机曾造成字段/动画不一致、原地发呆），也可能下一帧立刻重抽、根本不产生持续空档。
2. **派发器每帧调用**（NOTES:237，10540/12600）。若空签名 case 不排队动作，窗口长度取决于「多久后才排队下一个动作」，而不是插件能控制的 `HOLD`。这一点与 v33 的延迟落盘不同：v33 是人为按住 `+0x73E0`，用户方案是让游戏自己走原生空档 ⇒ **可能更干净，也可能只有 1 帧**。
3. **sig 非唯一 ID**：实机 V 行 sig 高度集中（91/124），19.7% 的块所有 case 同签名；FNV0 是所有空签名 case 共用一个值，放开后 `prev_hit_d` 判重会把它们互相命中，必须单独处理，否则要么全被否决、要么连续待机。

另需注意 P72 的 caveat「结构偏转只能改招式分布，改不出动作间隔」在**严格 `dE` 定义下成立**；但用户本轮接受「变相」（待机动作本身是一段低威胁时间），因此不能沿用 P72 直接否决，须改按「空签名命中 → 下一动作开始之间的帧差 / 玩家可攻击段」判据重新评估。P72 把该资料标为「未来放宽纪律时用」偏保守——本方案**不需要放宽任何纪律**，只是当时没按这个目标评估。

### 2.4 若推进：三阶段，先实证再改行为

| 阶段 | 内容 | 代价 |
| --- | --- | --- |
| ① 纯只读探针 | 在探针版加统计：疲惫态 / 非疲惫态各自 `sig==FNV0` 命中次数、**命中后到下一动作开始的帧差分布**、该段是否伴随 `e1=175`（倒地/待机动作号，跨怪未验证）或流口水动画 | 不编译行为版、零写入、复用现有 6 hook；需一场实机（可并进下一场自然任务） |
| ② 编译期开关 | 若①确认存在持续空档：疲惫态放开 `rise_weight_pick` 的 FNV0 排除，给 FNV0 一个独立权重槽（例如把疲惫形状从 `[60,20,14,6]` 改为按 `p5` 分流的「动作形状 / 待机形状」二选一），并为 FNV0 单独处理 prev 判重、限制每场次数与两次待机最短间隔，防原地发呆 | 只改编译期常量 + 一处候选筛选，不新增 detour；`W1_ALL` 等其它开关不动；保留一键回退 |
| ③ 跨怪 A/B | 至少 2 种怪，判据用「待机段平均/中位帧数、占战斗时长、玩家可攻击段」，**不用 `dE` / `gap`**；核对零 FATAL、无发呆/吼叫/动画错位、正常结算 | 需重新实机复验；P79 验收结论不再自动适用于改动后的成品 |

**效果上限参考**：v33 的原生 Think/进食窗口 11 次 / 315 帧 / 平均 28.6 帧 / 最大 45 帧，87~96% 被 `0xAFF40` 提前结束、实际平均 5~18 帧；用户 20:20 反馈「窗口里怪物做的是饮食动作」。本方案若成立，形态上仍是这类原生待机，**不能复刻 Rise `_tiredSec` / `_motRate` 数值**，也不能保证比 v33 更长。

## 3 · 结论

1. **Rise 疲惫不是抽选时间变长**：静态侧无此类字段；抽选层只换一组更单一、率恒 100 的池，状态层给持续时长，动作层给 0.8~0.98 的速度倍率，引擎/动画层给流口水与发呆（后者本项目无静态资产可定量）。玩家感知的「两招之间久」来自后两层，不是抽选器变慢。
2. **「疲惫态偏向待机权重」是目前唯一严格纪律内、且有 137 怪全量数据支撑的路径**：不插间隔、不写内存、不新增 hook、按 `sig==FNV0` 结构特征而非按怪/招式硬编码。成品 v2 的 `rise_weight_pick` 恰好把这类 case 排除在加权候选外，所以**改动点很小、路径是通的**。
3. **但当前仍是推断级，不能直接上线**：「空签名 = 可攻击待机」未实证，且派发器每帧调用可能让空档只有 1 帧；sig 非唯一 ID 会污染防复读。必须先做①的纯只读实证，再决定②③。
4. **v2 成品行为、P79 验收、P80/P83/P85 结论全部不变**；P72「严格 B 方案（语义映射）不可做」维持，本方案走的是**结构特征偏转**，与 B 方案不是同一条路，不冲突。
