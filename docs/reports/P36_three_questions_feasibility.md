## 0 · 先正面回答第 1 问

**是的，v50 本轮就是把 W1 单独拆出来落地验证。** 这不是遗忘，也不是把 W2 判定为不可行，
而是三个具体原因：

| 原因 | 说明 |
|---|---|
| **W1 零前置、收益最大** | W1 只需 `scan_cases()` 已有的 case 权重（v35 起实现、实机 `sw=100` 35/35 验证），纯局部计算即可把疲惫熵从 2.4519 压到 1.2955（Rise 1.2984）。不需要任何新实机数据 |
| **W2 有未定位的运行时输入** | Rise 侧 `range1..5` **只是文件名**，几何阈值数值在 `em131_00_range_data.user.2`（未抽取）；GU 侧离线 EMC 确有 `target_dist_rot` **147 处**、4 档 `('0','1','2','3')`，但 `h_matcher` 运行时 `s16` / 命中 case 索引 ↔ 档位 的对应**没有实机证据** |
| **避免两个未验证假设相乘** | 若同时写 W1 + W2，出错时无法区分是形状不对还是档位映射错。分开落地才能归因 |

**做 W2 需要的成本**：1 场纯只读探针（在 `0x8E144` 记录 `s16` / 阈值 case 序列 /
命中 case 索引 / `st3`），跨 2 只怪；对齐后 W1 就能升级为「(状态 × 距离档) 逐档 Rise 真实形状」。
若不想跑实机，也有降级方案：**按 case 索引分档**（不读绝对距离），但那是相对判据、还原度低，
我不会把它冒充 Rise 5 档。

**结论**：W1 先验、W2 待一轮探针，是我刻意选的顺序；你要我同时推进 W2 也可以，
只需同意「先跑一场 W2 只读探针」或「接受 case 索引降级方案」之一。

## 2 · 领地争夺（turf war）可行性

### 2.1 Rise 机制（公开资料中等可信 + 本地实证）

| 维度 | 结论 | 等级 |
|---|---|---|
| 性质 | **脚本化专属演出**（scripted combat phase），不是任意两怪相遇就走的通用 AI 分支 | 公开资料（monsterhunterwiki.org / Game8 / kikinote，多源一致，中等） |
| 触发 | 两只大怪同区相遇且路径交叉足够久；**猎人须在场**；**仅特定怪种组合**；离开近距离/视线后激昂消退；可用 Stinkmink 引怪 | 公开资料，中等 |
| 结果 | 按**怪种对组合表**固定 W / L / Draw；双方受伤、耐力大减、部位破坏，败者可操龙 | 公开资料（fandom MHRS Turf War List，中偏高） |
| 本地 RSZ | **`TurfWar` / `turf` / `Turf` / `Turfbattle` 全部 0 命中**；`Territory` 65 次全是地图区域 AI（`EnemyTerritoryInfo` 字段 `_BlockNo/_UniqueID/_Pos/_Radius/_CombatFlag`）；`rival` 80 次**全是 `Arrival` 子串误报**（`ArrivalTimeClient` 等） | **实证** |
| 本地资源 | 路径清单仅 1 条 `m00_territory.user.2`（第 381 行，**未解包**）；107 个已解包 `.user.2` 与 107 个 `rsz_json` **0 命中** territory/turf/battle | **实证** |
| 旁证（存疑） | 12 个按怪种编号的 `Em0xxVsRush*ActionCode` 空类、49 个 `ZakoCombat*` 小怪互斗类；不能等同大怪领地争夺 | 存疑 |

⇒ **本地 Rise 资料不足以实证复刻**；机制描述主要来自社区 Wiki，可信度中等。

### 2.2 GU 现状（实证）

- 多只大怪同场是任务数据一等公民（`docs/mechanics/quests.md:185,297-387`「+3 乱入」等；
  `mon-ai-entry.md:208-209`「每任务 6 只 `mEmType_N`」）。
- **有被动误伤、无主动互为目标、无专属演出**：公开资料两源一致（RGJ / GameFAQs）
  「won't actively target each other… attacks do damage each other and can even kill」。
- GU 动作名**闭集 13 类**（`FwMove/MoveMove/AttackMove/.../DemoMove`），
  **无 versus / turf 类**（`mon-ai-entry.md:233`）。
- 本地 249 篇 docs 全文检索无「相争 / 互殴」机制条目；`quests.md:171` 的
  「Tuff Turf」只是任务名。
- 引擎**能**枚举同区大型怪物及其怒状态（技能「同区大型怪物发怒时攻击+20」，
  `skills-arts.md:398`），但**代码锚点未定位**。
- 实机：v34 P6 多怪场可见 6 个 mon 对象 / 4 个 `sp`，但现有日志**不能证明同帧同区**。

### 2.3 三条路线可行性矩阵

| | (a) 纯只读观测 + W1 引导 | (b) 复用 GU 既有互殴做增强 | (c) 复刻 Rise 专属演出 |
|---|---|---|---|
| 需要 | 现有 5 hook + **新增** mon 区域号 / 对象表纯读路径；`forge_onUpdate` 快照 | 定位并**改写目标字段**；真正提交点 `0x76154`（当前可 hook，见 §1） | 演出调度 + 状态机写点 + **新增每怪一对动作/动画资源** |
| 写游戏内存 | **否** | **必须** → 违反零写入纪律 | **必须** |
| 改游戏资源 | 否 | 否（但增强演出仍需，见 c） | **必须**（`mot` / arc） |
| 硬编码怪种对 | 否 | 中 | **必然**（Rise 是固定组合表） |
| 跨怪通用 | 高（matcher 全怪共用） | 中 | 不可能 |
| **判定** | **有条件可行**，但「引导互攻」**不成立** | **当前条件不可行** | **不可行** |

**(a) 的关键限制**：EMC 只有距离 matcher、无「另一只怪」目标概念
（`docs/reference/formats/emc.md:51,63`：无视锥/听觉 opcode，`sub+0x30/+0x40` 归属未证）。
⇒ 纯只读最多做到「检测到同区两只大怪后，按状态调招式分布 / 更激进」，
**做不到让它们主动互攻**。这是引擎目标层的缺口，不是插件参数问题。

### 2.4 前置数据与最小验证

- **前置**：≥3 轮多怪任务（≥2 轮两只大怪同区 + 1 轮单怪对照）；
  纯读对象表基址 / stride / 活跃数（`mgr=*(main+0x184D750)` 是线索，
  但 `call(0x18FFC,mgr)` 是游戏函数调用，**禁用**）；mon 区域号；
  `0x8E144` 的 `s16` 与距离档对齐；新 hook 运行时首字校验。
- **验收门槛**：稳定复现「≥2 个不同 `sp` 的大怪对象在同一区域号、同一时间窗（≤120 帧）共现」，
  且零 FATAL / 零 `c0000005`、`hub=15` / `live=1` 不变。
- **最小步骤**：① 零成本离线：统计归档日志 `V/J/A` 行的 `sp`/`mon` 共现窗口；
  ② 1 场多怪实机纯只读对象表快照；③ W2 matcher 探针判定距离档的「目标点」
  是另一只大怪还是猎人 —— **若只指向猎人，则 (a) 的引导部分正式判不可行**。

> 一句话：**Rise 式领地争夺在当前工程条件下不可行**；唯一能推进的是
> 「多怪同区检测 + 招式分布引导」，且它不等于领地争夺。

## 3 · 小连段可行性

### 3.1 是真的（资源级实证，但表内部结构未解包）

| 证据 | 数值 | 来源 |
|---|---|---|
| combo 资源路径 | 解包二进制 UTF-16 扫描出 **73 个唯一** `emNNN_combo_NNN.user`，跨 em001(18)/em002(30)/em003(25)；**64/107** 个 `.user.2` 含 combo 字样 | `refs/rise_unpack/`（本轮现算） |
| 15 池 `_Category` | **{0:64, 1:36}**（TOTAL=100） | `out/rsz_json/em001_main_out1_*.json` |
| 「Category=1 → combo 目录」 | **强相关实证**：`tiredrange1` cat1=0 → combo 路径 **0**；其余 14 池 cat1>0 **均有** combo 路径 | 同上 + 解包配对 |
| `ActionTableData` | **仅 2 字段** `_Category` / `_TableNo` ⇒ 是资源句柄，连段序列在资源文件里 | `rszmhrise.json` |
| `ActionInfo` | 固定 8 字段，**无 combo/link/next/CD**；`explicit_cooldown_field_found=false` | `out/rise_ai_rules.json:427-441` |
| RSZ 模板 | `Combo` 784 次主语义是**玩家武器派生 / 操龙**（`PlayerComboTable`、`EnemyMarionetteComboAcceptData`），**无通用 `EnemyCombo` 类**；`Link/Chain/Rush` 是地图链接 / 物理链条 / 冲刺 | `rszmhrise.json`（150 个 Combo 唯一标识符逐个筛） |
| 公开资料 | mhvuze modding wiki：「**Combo files usually call for multiple Action files**」 | 社区权威 modding wiki，高（非官方/非反汇编） |

⇒ **Rise 的小连段是 `combo/` 资源里的预编排动作序列**：抽选层（L5/L6）决定
「进入哪张 action / combo 表」，执行层（L7）按表内序列推进。
**硬缺口**：所有 combo `.user.2` 都未解包，表内段数 / 是否线性 / 是否含条件分支 / 帧数
**本地无证据**；`TableNo→_actionNo→招式名` 映射链也断。

**证据等级更正**：「连段内部不重新抽选」是**高置信推断，不是实证**。
实证的是：`ActionInfo` 无连段字段、`_CheckPrevTableInfoList` 挂在抽选条件层、
`_IsActionEnd` 在 L3 门控、15 池内 TC 全 False；但「仅动作结束帧求值」
无反汇编佐证（P32 §2 已自述）。历轮 NOTES §409/472 的措辞应下调一档，**结论不推翻**。

### 3.2 GU 本来就有连段（实证）

- `+0x73E0` 四字节 = `act/sub/prev_act/prev_sub`（199/199、197/198 吻合）。
- **42.9%（51/119）相邻决策是 act 不变、仅 sub 变** ⇒ 连段段号，不是新出招（NOTES §403）。
- `2↔7` 转移 77 次是遁地/破土段号；`act=6` 固定序列
  `7/21→6/12→6/7→6/11→6/12→7/21`，段内 2~11 帧、`6/12→7/21` 恒 10 帧、重复 4 轮
  （NOTES §460/495/537）。
- **v22 零写入时仍是原版固定连段复读**（NOTES §764）⇒ 连段不是插件产物。
- 已证伪：v11/v12/v14/v15 事后写 `+0x73E1` 打断连段 / 拆成双攻击段，
  `rai_comboguard_v24i.nro` 反例归档**禁止再启用**（NOTES §455/472/843）。

### 3.3 v50 W1 会不会破坏连段？

**按设计不会，但目前是推断 + 一条待闭环数据**：

- 【实证】W1 只改 `h_matcher` 里**栈上局部**候选权重，`cs[].w` 绝不写回，
  唯一输出是返回分支偏移；5 hook 数量/点位不变、零写入。
- 【实证】GU 段内推进是固定段序列，不是加权抽选产物；prev 否决用 `+0x73E0` 高 16 位。
- 【**存疑·唯一风险口**】`NOTES:2042` 记「matcher **每条 EMC block 指令都会调**」，
  目前**没有实机证据**证明「段内 `sub` 变化时不经过 `op02/mode==1` 加权块」。
  若段内也走该块，W1 会改到段号分支。
- 【实证·判据缺口】`out/v50_sim_report.txt` 的 19 项 PASS **没有连段完整性项**，
  P35 §7 实机判据也未列 —— 这是本轮发现的一个实际待补项。

**闭环判据**：`sel>0` 只出现在 `act` 变化（新提交）、段内 `sub` 变化时 `sel=0`
⇒ 「W1 不破坏连段」由推断升为实证；反之 W1 必须加「段内豁免」。

### 3.4 三条路线可行性矩阵

| | (a) 原生连段不动 + 抽选点 Rise 规则（v50 现状） | (b1) 抽选层改变进入哪个连段 / 衔接概率 | (b2) 按状态改连段长度 / 段内衔接 | (c) 注入 Rise combo 资源 |
