# P96 · 「不能降速」结论修正：dttune 30-f32 数组的减速可行性（2026-11-16 21:40）

## 0 · 一句话结论

**P84/P89 的「动作速度只能加速、不能减速」下得太早，本轮离线侦察已证否其数据前提。** 该数组并非全 ≥1.0：59 只可定位大怪中，**17 只 `idx2` 原版即为 0.8**、**20 只 `idx3..12` 带 <1.0 值（最低 0.5）**。真正未定的是「哪个 idx 是动作速度、是否被 `0x10690ac` 钳制」，而这一分歧**从未被任何实验区分过** —— Titanbreak 只验证了加速方向，因为作者只需要加速。正确状态是「**待实验**」，不是「不可行」。

## 3 · 为什么不能直接照抄 Titanbreak（两个必须承认的事实）

1. **钳制点确实存在**：`0x10690ac` `cmp r7,#1; movle r7,#1`，随后 `strh [x+0x1428]+177` 写入动作速度 s16 族字段。若 idx1 确实走此路径，0.8 会被抬回 1.0。
2. **但该链入口 `0x1068DD8` 实机整场 T=0 未被调用**（P46 §9、NOTES:3109-3117，v45 hook 确已安装、首字非跳板）⇒ 只能说「静态反汇编存在钳制」，**不能断言实机会拦**；同理也不能断言「写 0.8 一定生效」。

两条叠加的正确表述：**字段归属与钳制生效性都待实验，而非已证否。**

## 4 · 三条路径与判定

| 路径 | 载体 | 疲惫专属? | 纪律 | 判定 |
|---|---|---|---|---|
| **A. 静态改倍率（Titanbreak 同款）** | 单条目补丁 arc，`arc_tool.py pack --orig` | ✗ 全局（任务加载一次性生效） | ✅ 零 hook / 零写入 / 不新增 detour | **可试，2 场短实战即可定字段** |
| B. 解钳制后静态改倍率 | IPS32 改 `0x10690ac`（`movle r7,#1`→`mov r7,#0`） | ✗ 全局 | ⚠ 代码补丁，但不新增 hook（与 HP 条 NOP 同构，走既有 IPS32 通道） | 若 A 证明 idx1 被钳，则 B 是唯一解 |
| C. 找 `idx3..12` 中的疲惫槽 | 注册表 `0x3ccff8` 参数节点 dump，绑定 idx3..12 | **可能 ✓** | ✅ 纯数据层 | 唯一可能「疲惫专属 + 零 hook」，但需新 RE 工作 |
| D. 运行时按状态写参数槽 36 | 新 hook + 写内存 | ✓ | ❌ 违反零写入 + 6-hook 固定 | 仅在用户明确放宽纪律时考虑 |

**必须一并说明的限定**（P88/P89 仍然成立的部分）：即便降速做成，它只拉伸动作持续 `dS`，**不产生两招之间的空档 `dE`**。按用户定义「输出窗口 = 两招之间间隔变长」，降速给的是「怪物整体节奏变慢、每招占用更久」，不是「招与招之间多出时间」。两者对玩家的手感收益不同，不可混为一谈。
