## 2 · v63 强制放大为何一次都没触发

`J f=` 与 `G f=` 均为 **0**，`S` 行 `gdone=0`。`h_stamina` 已成功安装（`first=E92D41F0`，非 IPS32 跳板，`STAM_SITE_OK=1`），因此卡在 `h_stamina` 的门控条件：

```
DRAIN_ENABLE==1 && DRAIN_DONE==0 && STAM_SITE_OK==1 && GATE_LIVE==1
&& LOW==0 && f>=1800 && A_N>=20 && a1<0
&& act!=0 && 0<thr<0x4000 && st5==0 && cur>0 && an>=4
```

三个嫌疑（按可能性排序，本场日志无法区分，已加 `DG` 诊断行留待下一场定案）：

1. **`LOW` 门控**：`LOW` 由每 300 帧动作增量判定（`da<=2` 连续两次置 1）。本场 `BEAT act=295` / 46800 帧 ≈ **1.9 动作/300 帧**，长期贴近阈值，`LOW==0` 很可能长期不成立。
2. **`thr = rd16(act+0x5D84)`**：P33 定案 `0<thr<0x4000` 用于排除 `65535` 免疫哨兵；本场怪种（`sp=0020` 轰龙）该值可能为 0 或 65535。
3. **触发源可能是链 II 减气而非链 I 耐力扣减**：P29/P30 定案 `0xA30E4` 的 `counter>=thr` 可直接通知疲惫 FSM；若本场由减气触发，`0xBD260` 负 delta 调用可能很少走到门控。

**推论**：本场自然疲惫只需约 5–6 分钟，远短于 P63 按雄火龙 `d0=-8` 外推的 15 分钟。**强制放大的边际价值下降**，且它会在 W2/W3 数据里混入非自然状态段。故 v64 把 `DRAIN_ENABLE` 置回 0（代码与常量全部保留，需要时改一个常量重编译即可）。

### 2.1 追加离线定案（15:10，无需新实机）：J=0 的原因就是 `LOW` 门控

```
N f=5700  ENTER-LOW dA=0 lowhits=2 a=16
N f=21600 EXIT-LOW  dA=8 lowhits=0 a=26
N f=22200 ENTER-LOW ...（之后反复 ENTER/EXIT）
```

- `LOW` 在 **f=5700 就置 1，直到 f=21600 才退出**，连续 15900 帧（≈265 秒）`LOW==1`。

⇒ **`J/G=0` 已定案为 `LOW` 门控，与 `thr`、链 II 无关；v64 的 `DG` 诊断行不再是必需项。**
若要让 v63 式温和放大真正生效，只需把 `LOW==0` 从 `h_stamina` 门控里去掉或改为「仅在高活动段放宽」——这是编译期小改，不需要实机采样。

### 2.2 追加离线定案：`ZT=0` 不再阻塞高保真 W2

P60 的离线全量表已齐备：`out/dist_bands_all.json` = 137 怪 / 8488 距离块 / **119 怪的 4 档 f32 阈值行**（例 `em032` = `[450,1000,2700,5000]`、`[500,1000,3000,5000]`），`out/rise_band_shapes.json` = **15 张 `(state,band)` 形状表 + Rust `BAND_SHAPE` 常量**。

⇒ **P61 的运行时表链路线可以彻底放弃**，P60 路线 B 的「编译 137 张表 + 基址锚定」前置也随之下调为「可选的高精度标定」。W2 高保真加权现在只剩纯离线编码工作。
