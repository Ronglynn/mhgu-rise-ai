# P85 · 「输出窗口」口径定案 + Rise 节奏倍率可复刻性复核

2026-11-15 22:12 · 用户两问的只读复核，无实机、未编译、未改插件/部署/源码、GitHub 远端零操作。

## 0 · 用户口径（本轮起作为唯一判据）

> 「留输出窗口」= **怪物在疲劳状态下，两招之间留给玩家的攻击窗口长，即两招之间的间隔时间长**。

对应本项目早年定义的 `dE` = 动作结束（END）→ 下一动作提交（START）的空档，即「输出窗口候选」（NOTES:542）。
必须与另外两个指标严格区分：

| 指标 | 定义 | 本项目出处 |
| --- | --- | --- |
| `dE`（本轮判据） | 上招 END → 下招 START 的**空档** | `analyze_actionend_log.py` / NOTES:542 |
| `dS` | 动作本身时长（中位 85 帧 ≈1.42s） | NOTES:560 |
| `gap`（AE 行） | 相邻动作类边沿帧差 = **动作周期**，含 dS | `lib.rs:2719-2722` `f - LAST73F`；P70 §2 表格的 `gap p50` |

⇒ **动作速度倍率只作用于 dS，不作用于 dE**；`gap` 变长不等于空档变长。这是第二问的判定基础。

## 1 · 按该口径，v2 做到了没有 —— 没有，且 GU 原版没有可被拉长的阶段

1. **函数级硬证据**：v17 实机 `0x75224`(action end) 主对象 162 个 E，全部在 1 帧后产生 1 个 S，配对 162/162 无例外 ⇒ **END → 下一提交恒 1 帧，GU 原版架构里不存在「动作结束后的间隔」这一阶段**（NOTES:558）。v25 复核常规链为 `END(0x75224) → 0x76154 → 0xAFF40`（NOTES:962-964）。
2. **v2 能力边界**：W1/W2/W4 只改抽选权重形状（抽到哪个 case），W3 三次实机 `gs=0` 结构性失效（`W3_GATE_ENABLE=0`）；没有一层改动作持续、提交节奏或插入待机（P70 §2、P79 §6、`out/release_profile.md`）。
3. **实机判据**：
   - P70（v69 斩龙，疲惫窗 4226 帧≈70.4s）：每千帧动作数 PRE **10.5** → TIRED **12.4**（+18%），`gap p50` 52→69，两口径方向不一致；定案「怪在流口水的同时仍持续出招，没有喘息段」。
   - P79（v71 泡狐龙，窗 4467 帧≈74.5s）：旧判读误报「密度下降 47% ⇒ 喘息」，校正按疲惫态 AR 识别主怪 + BEAT 全量交叉后，窗后动作归零使比较失去基线 ⇒ 判「**不可判**」，P70 定案维持（P79 §4、§6）。
   - ⇒ 两场都不支持「疲惫态两招间隔变长」。

## 3 · Rise 侧「倍率」到底有哪些字段

| 字段 | 静态实证 | 语义 / 边界 |
| --- | --- | --- |
| `EnemyStaminaData._motRate` | 78 个 `stamina_data`，**60/78 非 1.0**，值 0.8~0.98、7 种（P80 §(c)） | **动作播放速度倍率**（字段名 [B]，作用语义无 Rise 反汇编/实机 [C]）；按怪参数化，不是常量 |
| `EnemyStaminaData._tiredSec` | 61/78 非零，30~120 秒、12 种值 | **疲惫状态持续时长**，不是两招间隔 |
| `EnemyThinkTimerData._Timer` | 0/3/5/…/300 秒，17 档 | 思考 / 重复抑制计时器（配 `_CheckPrevTableInfoList`）；**P32:120 明确「不是疲惫时长，勿混用」**；`explicit_cooldown_field_found=False` |
| `ActionInfo._tiredMotSpeedLowerLimitValue` | 3 个 `action_param_data` 中仅 16/16/10 个动作显式 1.0，其余 -1.0 | 逐动作速度下限；无证据证明它拉长硬直（P72 §6） |
| 15 池 `_TransitionRate` | 555 池率和恒 100 | 抽选概率，已在 W1/W2/W4 复刻形状；不改变节奏 |

**关键结论：Rise 静态侧不存在「两招间隔倍率」字段。** 玩家可感知的流口水 / 发呆 / 输出窗口来自 FSM 与动作资源层，而 `action/combo/motion/message/actiontune` 类文件 442 条清单中 437 条 0 覆盖（P32:168-171），全部 Rise 结论均为静态复核、无 Rise 实机或反汇编（P32:201）。Rise 侧还有 12 Hub / 15 池的表号集合差异，但那决定「出哪招」，不决定「招与招之间空多久」。

## 4 · 「复刻 Rise 倍率」的三条路径判定

### 4.1 静态数据层（Titanbreak 范式）—— 对「疲惫」不通
P84 已证：改 `emNNN_SS_dttune` 的 30 个 f32 怒时倍率数组即可改运行时倍率，零 hook、零写入、任务加载时一次性生效。但：
- 该数组属 `cAngryParam` / `angryprm` 族，**怒时专用**，运行时不随疲惫状态切换；GU 数组后 16 项全 1.0，静态侧未定位疲惫专属动作速度槽（Rise 对应 `_tiredMotSpeedLowerLimitValue`）。
- 数值方向相反：Rise `_motRate` 0.8~0.98 全部 <1.0；而 wiki §3bis 的绑定链「参数槽 36 → 动作速度 s16 `[x+0x1428]+177`」在 `0x10690ac` 有 **下限钳制 ≥1.0**（`cmp r7,#1; movle r7,#1`），即该通道结构上只能加速、不能减速。P84 §分歧已用 Titanbreak idx2 的 `1.0→0.9` 点出同一矛盾。
- **证据等级标注**：① wiki 的 idx0/1/2 绑定与 Titanbreak 010 模板 `SpeedMult/AttackMult/DefenseMult` 顺序相反，两边都非代码级 [C]，P84 已把 wiki 绑定降为「存疑，需参数槽 dump / 实机 A/B」；② 该怒分支分发头 `0x1068DD8` 在 v45 实机 **T=0 整场一次未被调用**（NOTES:3109-3117），`0x1069D8C / 0x873C` 同判死代码。⇒ 钳制是**静态反汇编级约束**，不能当实机定案；但也不足以支撑「把 0.8 写进去能生效」。

### 4.2 运行时按疲惫状态缩放 —— 违反纪律
写参数槽 36 / `[x+0x1428]+177` = 游戏内存写入 + 新增第 7 个 hook，违反「零游戏内存写入」与「6 hook 固定」两条纪律；且可能直接被 ≥1.0 钳制吃掉。属另一条技术路线，须重新实机复验。

### 4.3 零写入近似：状态化延迟落盘 —— 唯一贴合用户定义，但只能「造窗口」不能「复刻数值」
复活 v33 的延迟落盘，用现成疲惫判据 `act+0x505>=2`（或 BEAT 判据）门控，仅在疲惫态延长 HOLD / 降低 COOL，其余状态不干预：
- **符合纪律**：零写入、跨怪通用、不按 action_id 硬编码、可复用现有 `0x76154` hook（不新增 detour）。
- **继承硬上限**：87~96% 窗口被 `0xAFF40` 提前结束，加大 HOLD 无效；要可控 45 帧级窗口必须做 `0xAFF40` 层双延迟（从未实施，且 v21i 曾因跳过 `original!` 出现原地发呆）。
- **形态不对标**：窗口内是 GU 原生进食 / Think 动画，不是 Rise 式流口水喘息；且无法把 `_tiredSec` / `_motRate` 的按怪数值映射进去（GU 没有对应状态绑定槽）。
- 结论：可做出「疲惫时偶尔多出 5~45 帧空档」的近似，**不能称为复刻 Rise 倍率**；需另开一轮工程 + 实机 A/B。

## 5 · 最终结论

1. 按用户定义，「输出窗口」= `dE` 空档。**v2 没有实现；GU 原版 dE 恒 1 帧，根本不存在可被倍率拉长的间隔阶段**。P70 的「密度 +18%」与 P79 的「不可判」都不支持该效果。
2. **Rise 静态侧没有「两招间隔倍率」**，只有 `_motRate`（动作速度）、`_tiredSec`（状态时长）与思考计时器；动作速度倍率只拉伸 `dS`，不产生空档，动作判定/后摇同比变慢 ⇒ 即使 1:1 搬数值也不等于有输出窗口。
3. **数值可搬、通道不可挂**：GU 的静态倍率数组是怒时专用且疑似 ≥1.0 钳制，疲惫态无数据槽；运行时写入违反现有纪律。唯一纪律内路径是 v33 式状态化插间隔（曾实机跨怪 PASS 但上限 5~18 帧、窗口是进食动画、已被用户拍板路线 A 取代）。
4. **v2 成品行为、P79 验收、P80/P83 达成度结论全部不变**；本轮只把「疲惫喘息不可复刻」的理由精确化为「dE 阶段不存在 + Rise 无间隔倍率字段 + GU 疲惫态无倍率通道」，并补上 v33 历史路径的复盘与 ≥1.0 钳制这条静态约束。
5. 若用户要推进：下一步是**行为层另开一轮**（状态化 HOLD 或 `0xAFF40` 双延迟），需明确放宽「不新增写入 / 不改提交时序」中的哪一条，并在编译前定好回退链与实机判据（窗口时长按 `dE` 而非 `gap` 统计）。本轮不实施。
