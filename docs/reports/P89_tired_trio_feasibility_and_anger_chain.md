## 0 · 结论

| 项 | 判定 | 一句话 |
|---|---|---|
| ① 换一批更单一的候选 | **代码已实现，但实机覆盖率极低 ⇒ 唯一纪律内可推进项** | W1/W2/W4 已有 tired 低熵形状，但 P70 `wt=7` / P79 `wt=1`（全场疲惫形状应用次数），W1 全场成功仅 63 次；GU 只有一张 `*_cmdtbl`，**候选集合换不了**，只能改同一批 case 的权重 |
| ② 状态持续 | **不需要做，也做不了** | GU 原生疲惫由引擎层 FSM 维持到进食/耐力回升（P19/P46/P87）；按 Rise `_tiredSec` 30~120s 定量控制需写 `em+0xCAC8` / `act+0x408` 或改 `durF`，违反零写入，且 `durF` 实证无效 |
| ③ 动作变慢 | **不可行，且方向可能相反** | GU dttune 30 f32 是怒时专用、任务加载一次性生效、无疲惫槽，`0x10690ac` ≥1.0 钳制只能加速；即使做成也只拉伸 `dS`，按用户定义「输出窗口 = 两招空档 `dE`」不产生窗口，甚至可能因判定/后摇变长而缩短可攻击时间 |

**前提需澄清**：「GU 侧疲劳是计时的」只在「减气阈值计数 / 动作剩余计时器」意义上成立；**疲惫状态本身的持续不是计时器**。详见 §1。

## 1 · 前提澄清：GU「疲劳计时」到底指什么

项目里存在两类被混称「计时」的量：

| 类别 | 字段 / 位置 | 定案 |
|---|---|---|
| **计时/计数（成立）** | 减气蓄积 `act+0x5D82` counter、`0xA3198 grow` 阈值递推、`dttune` Exhaust `[initial,A,B,durF,increase,max]` 的 `initial` 触发点；`act+0x1BC` 逐帧 −1 的**动作剩余计时器**（40.0→0，值域 0..240）；`+0x5C` FSM 浮点计时器 | P19 字节级 + 实机闭环：`initial=150` 就是流口水触发点；NOTES:670 |
| **疲惫状态持续（不是计时器）** | wiki §4：「多数怪 `durF=0` = 无计时（由进食/超时结束）」「即时型 = 维持到怪物进食/规定行为结束」；P46 恢复段 `+0x505==3 且 +0x508!=0 → 0xBD184(mon,0)`；P20「疲惫结束条件是进食/耐力回升，不是计时器」 | **本项目定案**，P87 据此写「疲惫结束不是计时器」 |
| **有字段但实机不走** | 离线反汇编 `0x106901C vstr s0,[r4+0xCAC8]`（疲惫计时器）、`0x1068F9C strh r0,[act+0x408]`（疲惫时长）、分发头 `0x1068DD8(em,r1=2)` | **`0x1068DD8` 实机 T=0 整场未调用（死代码）**，NOTES:3558；属静态约束，不能当可调旋钮 |
| **部分怪有固定时长** | 角龙 `durF=600`（10 秒） | 但项目实证 **`durF` 对减气无效**（P35/P40，`initial=0` 反致连续硬直），且块偏移逐怪浮动、定位不可靠（NOTES:3292-3308） |

⇒ 准确说法：**GU 的「进疲惫」由减气计数 + 阈值触发，「出疲惫」由进食/耐力回升结束，中间没有插件可写、实机会走的固定时长计时器。** 若用户记忆中的「计时」指 P79 的「自然疲惫窗 74.5 秒」，那是**日志观测到的时长**，不是机制字段。

## 2 · 三项逐条判定

### 2.1 换一批更单一的候选 —— 已实现，但实机几乎没生效

**成品现状**（`plug/_release_build/src/lib.rs`）：
- `BAND_SHAPE[state*5+band]` 15 组，tired 五档 `[65,25,10,0] / [45,45,10,0] / [45,45,10,0] / [50,40,10,0] / [70,20,10,0]`（熵 1.1568~1.3690），另有 `SHAPE_T3` 降级形状；`:1023`。
- `mon_state()` 用 `act+0x518==1 → ST_ANGER`、`act+0x505>=2 → ST_TIRED`；`:1536`。`rise_weight_pick()` 按 `eff`(stance 修正后的 st3) 取形状，`wm=3` 表示疲惫形状；`:1592-1627`。
- W1 全抽选（`W1_ALL=1`）、W2 按 `(st3,band)`、W4 按 12 处境分流；`W3_GATE_ENABLE=0` / `DRAIN_ENABLE=0`。

**实机覆盖率（本轮关键发现）**：`W3_N/W4_N/WT_N` 按 `wm` 分类，`WT_N` 专门计疲惫形状（`:2180-2182, :2218-2220`）。
- P70（斩龙，疲惫窗 4226 帧≈70.4s）：**`wt=7`**，`T3=[60,30,10]` 在起作用，但结论是「流口水同时仍持续出招」。
- P79（泡狐龙，自然疲惫窗 4467 帧≈74.5s）：**`wt=1`**，而 W1 全场 `wall=116 / wnok=63`。
⇒ 疲惫形状在两场里分别只应用 7 次和 1 次，**不是「没实现」，是「几乎没跑起来」**。可能原因（未逐一实证，勿当定案）：疲惫窗内主轨抽选本身稀疏、`W1` 要求 `sw==100 && n>=4 && main_track`、以及 **W4 在 `hub==3`（换区/离场）时直接 `return (-1,0,0)` 主动不套形状**（`:1605-1610`）——而 P87 重判发现疲惫窗 6 段长空档恰与 7 次换区信号重合。

**可推进性**：这是三项里**唯一严格纪律内可行**的（零新增 hook、零写入、跨怪通用）：放开/调整疲惫态形状应用条件、处理 `hub==3` 与疲惫态的冲突、提高低熵形状覆盖率，只需编译期开关 + 一轮实机 A/B。

**两条边界**：
1. GU 只有一张 `*_cmdtbl`，**没有 15 张独立池表** ⇒ 做不到 Rise 的「换表号集合」（tired 池表号并集 `{1,15,20,51}` vs 常 `{13,19,20,51,79}`）；现有实现是「同一批 case 的权重更集中」的**机制级近似**，不是 1:1。
2. 低熵 = 出招更单一 / 复读感更强（P72），P70 疲惫窗动作密度反而 **10.5→12.4（+18%）**。若目标是「留输出窗口」，把权重压到 top-1 方向可能相反；与 P87 的 FNV0「让位」方案（放开空签名 case）在同一处存在设计冲突，必须一起定，不能两头都压。

### 2.2 状态持续 —— GU 原生已有，插件不该造

- 原生链：`+0x508` 耐力 → `+0x505` 状态字 → `Stamina_low_Start/tired_start/tired_Loop` FSM（P46），P19 实机达到 `initial=150` 后**立刻停止出招、开始流口水**（连续 0 动作段）；恢复靠进食 / `0xBD184(mon,0)`（P20/P46/P87）。P79 场重判出 **6 段 ≥300 帧空档、最长 928 帧≈15.5s**。
- 若想按 Rise `_tiredSec` 30~120s（61/78 怪非零，P80）**定量控制时长**：需要写 `em+0xCAC8` / `act+0x408` / `dttune durF`，或调用 `0x1068DD8(em,2,0)`。三条都违反「零游戏内存写入 + 6 hook」纪律；且分发头实机 T=0、`durF` 实证无效 ⇒ **改了也不生效**。
- 纪律内唯一近似是 P87 的**让位**：用 `_SetMeatRecovStartPoint`(20/30) / `EndPoint`(70/80) 作为**门控条件**，`_mapNikuEatSec`(20s) 只作护栏，让抽选层在原生疲惫/进食期间不打断，**不控制状态时长**。

### 2.3 动作变慢 —— 静态层不通，且对目标可能反效果

- **静态数据层（P84 Titanbreak 范式）不通**：GU `dttune` 30 个 f32 是 `cAngryParam` **怒时专用**、任务加载时一次性生效、不随疲惫切换；后 16 项恒 1.0，无疲惫专属动作速度槽。wiki §3bis 把 idx1 绑 `MotionSpeedRate` / 参数槽 36 / `[x+0x1428]+177`，`0x10690ac` 有 **≥1.0 下限钳制（只能加速）**，Rise 的 `_motRate` 0.8~0.98 全在钳制区、方向相反（P85）。Titanbreak 模板与 wiki 的字段顺序还互相矛盾，两边都非代码级。
- **运行时路径**：写参数槽 36 需写游戏内存 + 第 7 个 hook，违反纪律；且该分发头实机 T=0。
- **方向问题（最重要）**：`_motRate` 只拉伸 `dS`（判定帧 / 后摇同比变慢），按用户 22:12 明确定义「输出窗口 = 疲惫态两招之间空档 `dE`」，`dS` 变长**不产生 `dE`**；动作判定与后摇占用更久，玩家可安全输出的空档可能不变甚至更短。⇒ 即使放宽纪律做成，也不该当作「留输出窗口」的手段，只能算「体感 Rise 化」，需单独实机 A/B。

### 3.2 Rise 侧

- L0 `EnemyUserDataParam._angerData`（58 字段之一，**数值未解包**）。
- L4 `angerRange1..5` 池：平均 **3.60 候选**、熵 **1.6740**（常 1.6669，仅差 +0.43%）、表号并集 `{14,19,20,61,62,80}`，**独有 14/61/62/80** ⇒ **发怒的差异在「可用招式集合」，不在概率集中度**；抽选层实际只区分「疲惫 vs 非疲惫」。
- 逐动作 `_angerMotSpeedUpperValue`（P88 本轮重解析）：856 个 `ActionInfo` 中 **762 个 −1.0 禁用、93 个 1.0、1 个 1.1**(em003) ⇒ 怒时加速是**上限保护**，不是普遍倍率。
- 反向因果：`ActionInfo._subStaminaPoint`（15~25% 动作非零，值 5~100）逐动作扣耐力 ⇒ 用哪些招决定何时进疲惫，与怒链共用 `ActionInfo`。

### 3.3 v2 里的接入

`mon_state()` 优先读 `act+0x518==1` → `ST_ANGER`；`BAND_SHAPE` anger 五档 `[40,30,30,0] / [35,25,25,15] / [35,25,20,20] / [50,25,15,10] / [70,20,10,0]`，与 normal `[45,30,25,0]…[35,25,25,15]` 差异很小。P79 `st3=[0,1,2]` 全覆盖，但 **状态分化主要体现在 tired**，所以「发怒状态匹配出招」在 v2 里很弱——这与 Rise 静态结论（怒/常熵几乎相同）一致，不是缺陷。

## 4 · 与 v2 及达成度的关系

- **v2 行为、P79 验收、P80/P83/P85/P86/P87/P88 结论全部不变**；本轮未做任何改动。
- 若推进 ①，属于**在既有 W1 框架内提高覆盖率**，不是新增机制；但改动后 P79 验收不再自动适用，需重新实机 A/B，且判据要同时看「疲惫形状应用次数 `wt`」与「低动作段帧数」。
- 若要达成用户真正的目标（输出窗口），**主路径仍是 P87 的 FNV0 让位**；① 与它必须联合设计（疲惫态不能既把权重压到 top-1，又放开空签名 case）。
- ② ③ 不列入待办：② 原生已有，③ 通道不通且方向相反。
