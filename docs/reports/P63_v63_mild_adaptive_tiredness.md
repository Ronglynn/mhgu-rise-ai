# P63 · v63 温和自适应疲惫放大（单场补齐 `st3=2` 样本）

日期：2026-11-15 14:10 · 状态：**已编译部署，未实机** · 部署 md5 `8702a7a6908c778e39106ba38cd9c34e`

## 0 · 结论

用户：「自然疲惫太久，能不能复用之前的疲劳方案，就是放大倍率，但这次调小倍率让在攻击 1-2 分钟后疲劳」。

**能，已做成 v63。** 复用的正是 v55/v56 已实机 PASS 的 `0xBD260` 入参 delta 放大通路（改参数、零游戏内存写入、游戏自己走 `0xBD2B8` 耗尽分支），但把**固定倍率 ×64 换成自适应温和倍率**：每次负 delta 扣 `base / 8`（`base` = 该槽首次放大时的当前耐力），约 **8 个动作 ≈ 1.5 分钟**后由游戏原生进入疲惫，随后是约 80 秒的流口水窗，正好给 v62 的 W2/W3/W4 一次性探针补上一直缺的 `st3=2` 样本。

**这是采集配置，不是成品**：`DRAIN_ENABLE=1`，J/G 诊断行会重新出现；成品发布前必须置 `DRAIN_ENABLE=0` 重新编译（回退纯只读 v62）。

## 1 · 定量依据

### 1.1 为什么不能直接用「固定小倍率」

| 来源 | 数据 |
|---|---|
| v56 实机（雄火龙） | `d0=-8`，`cur=650`，×64 → `d1=-512`，**2 个动作**耗尽（P52） |
| v53 实机（雷狼龙） | `d0=-50` → ×64 时 1 个动作耗尽 |
| 负 delta 动作间隔 | v56 日志 `J f=4105 → 4772` = **667 帧 ≈ 11.1 秒 @60fps** |
| 耐力无持续恢复 | v56 日志 `f=2550..4050` 槽 0 `t508` 恒 **650**；只在疲惫结束时一次性回 800（P48 §3.1 未定案，本场数据支持） |
| 自然疲惫外推 | `650 / 8 ≈ 81` 个动作 × 667 帧 ≈ 54,000 帧 ≈ **15 分钟** |

固定倍率 `M` 下，耗尽所需动作数 = `base / (|d0| × M)`；`|d0|` 跨怪差 6 倍 ⇒ 同一个 `M` 在雄火龙与雷狼龙身上耗时差 6 倍，直接违反项目「AI 改动必须跨怪通用、禁止按单怪 action_id / 怪种硬编码」纪律。**所以「调小倍率」要调成自适应，而不是调成一个更小的常数。**

### 1.2 v63 的等效倍率

`step = base / DRAIN_TARGET_ACT`，`DRAIN_TARGET_ACT = 8`；**不再用 `d0` 计算扣减量**，因此与怪种、动作消耗表完全解耦。

| 怪 | `base` | `step` | 等效倍率（相对 `d0`） | 预计耗时 |
|---|---|---|---|---|
| 雄火龙 | ≈650 | ≈81 | ≈10× | 8 × 11.1 s ≈ 89 s |
| 雷狼龙 | ≈1000 | ≈125 | ≈2.5× | ≈89 s（动作间隔相近时） |
| 任意怪 | 任意 | `base/8` | 自动适配 | ≈8 个负 delta 动作 |

开局仍有 v50 的合法性门控（`f>=1800`、`A_N>=20`、目标槽 `ST_AN>=4`、`LOW==0`、`0<thr<0x4000`、`+0x505==0`），v56 首次放大发生在 `f=4105`（含跑图/接敌 ≈68 秒）。所以**从接敌开打起约 1.5 分钟，从任务开始约 2.5 分钟**；仍远短于自然疲惫的 15 分钟，且不像 v56 那样 1~2 个动作就倒。

## 2 · v63 实现（唯一改动在 `h_stamina` 放大计算）

```
const DRAIN_ENABLE      = 1;   // 采集配置（成品须 0）
const DRAIN_MODE        = 1;   // 1=自适应温和；0=回退 v56 固定 DRAIN_MUL
const DRAIN_TARGET_ACT  = 8;   // 目标动作数
const DRAIN_DEADLINE_AN = 20;  // 逻辑动作数兜底
static DRAIN_BASE[NMON], DRAIN_ACT[NMON], DRAIN_AN0
```

- 每个负 delta 动作：`step = base/8`，`delta = -step`。`base` 取该 `slot_of(a0)` 首次放大时读到的 `+0x508`，存在插件自己的静态数组里（**不是游戏内存**）。
- **双重兜底（都用动作计数，免疫暂停）**：
  1. 第 8 次放大、或 `cur <= step`、或该槽 `ST_AN` 自首次放大增长 ≥20 ⇒ 改用 v55 范式 `-(cur+1)` 一次性扣光（P49 实机 PASS）。
  2. 帧兜底原本写了 9000 帧，**已删除**：项目既有定案「暂停菜单不冻结 `forge_onUpdate`」，用户又多次暂停看日志，forge 帧会让恢复后的第一个动作立刻误触发兜底。
- `DRAIN_DONE` 在游戏自己进入疲惫（`a505>=1 || a508==0`）后熔断，**单窗**；疲惫结束恢复原样透传，不再放大。
- J/G 行格式**逐字节不变**（判读仍靠 `d1` 序列识别：前 7 次 `-81`、最后 1 次 `-(cur+1)`）；`DRAIN_BASE/ACT/AN0/DRAIN_DONE` 随 epoch **不**重置。

**逐字节不变**：W1 抽选主干、Z/ZP/ZS/ZT（W2）、AE/QX（W3/W4）、6 个 hook、`PROFILE_RELEASE=1`（R/W 仍关）、`W1_ALL=1`、`6_启动并抓日志.bat`、`load_order.txt`、既有日志格式。**零游戏内存写入**（只改 `0xBD260` 入参 delta）。

## 4 · 假设清单（无实时证据，明确标注）

1. **耐力无持续正 delta 恢复**：v56 实机 1500 帧恒 650 支持，但 P48 §3.1 明确「恢复来源未定案」。若某怪存在持续恢复，8 次 `step` 可能扣不光 ⇒ 由两个兜底保证窗一定出现。
2. **负 delta 动作间隔 ≈667 帧** 由 v56 单场雄火龙外推；轰龙/其它怪、不同打法会有偏差。故用「动作数」而非「秒」做主判据，用户感知的「1-2 分钟」是期望值不是硬保证。
3. **疲惫窗时长 ≈4764 帧（79 秒）** 沿用 P49 定案（雄火龙）；雷狼龙 P53 约 3453 帧，按怪种不同。
4. **`base` 取首次放大时的 `cur`**：若首次放大前耐力已被自然扣掉一部分，`base` 会偏小，但 `step` 同比例缩小，仍是 8 个动作耗尽，不影响结论。
5. **单窗足够采 `st3=2`**：若本场疲惫窗落在任务末尾或探针样本偏少，需要下一轮把 `DRAIN_DONE` 改成疲惫结束后可重置以产生第二窗（本版未实现）。
