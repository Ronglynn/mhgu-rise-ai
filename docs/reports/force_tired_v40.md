动作必定疲劳），使本轮不靠运气就能定案疲惫状态字段。已同意方案 B。

**产物 `out/rai_force_tired_v40.nro`（`be9cf246…`，36864 B，无游戏进程时已部署）。**

## 1 · 实现选择：写「减气蓄积」而不是「耐力上限」

用户给的两个候选里，选了**第二个（一个动作必定疲劳）**，原因是可定位性：

- **耐力上限 / 当前耐力**的运行时字段在现有逆向资料里**没有确证**
  （只有静态参数类 `StaminaSubRate` @`cEmDouMouKaData+0x14`、
  `StaminaTimeVal` @`+0x20`、`cEmStaminaData::cStaminaLev`，都是
  XML/类成员注册名，不是 mon 实例里的可直达偏移）。盲写风险高。
- **减气（Exhaust）蓄积**有完整代码级链路，见下。

而且写蓄积值属于**自然状态机路径**：游戏自己判定「蓄积 ≥ initial → 疲惫」，
插件**不写 `mon+0xCAC4` 状态字**，所以观测对象不被污染 —— 这正是用户
描述机制的正确实现方式。

## 2 · 离线定位链（全部 capstone 反汇编 [C words]）

数据源 `refs/hpbar/main_text_decomp.bin`（文件偏移 = `main+0x...`）。

**(a) 状态字**（21:17 已确证）：`0x1068E08 / 0x1068E2C`
`ldr r0,[r7,#0xCAC4]!; cmp r0,#1 / #2` ⇒ `*(u32*)(mon+0xCAC4)` = 1 怒 / 2 疲。

**(b) 状态对象基址**：`0xA398C` 函数入口
```
0A3990  mov  r4, r0              ; r0 = mon
0A39A0  mov  r8, r4
0A39A4  ldr  r1, [r8, r1]!       ; r1 = 0x1428 ⇒ r8 写回 mon+0x1428
                                  ; r1 = *(mon+0x1428) = act 对象
```
⇒ 状态块在 **act 对象**（即 `ident(a0)`）里，不是 mon 本体。

**(c) 状态遍历**：同一函数按
`bl 0x71078; ldr r7,[mgr+0x34 / 0x38 / 0x3C / 0x40 / 0x44]`
依次处理 Poison / Sleep / Para / KO / **Exhaust**，与 `monster_status`
的 8 行顺序一致。Exhaust 段 `0xA3B9C..0xA3C04`：
```
0A3B9C  ldr  r0, [r8]            ; r0 = act
0A3BA0  movw r1, #0x5d82
0A3BA4  add  r6, r0, r1          ; r6 = act+0x5D82
0A3BA8  ldrsh r1, [r6]           ; 蓄积计数（u16）
0A3BB4  movw r1, #0x5d88
0A3BBC  add  r5, r0, r1          ; 衰减 f32 timer
0A3BE4  sub  r0, r1, r0          ; 每 A 帧减 B
```
⇒ **`*(u16*)(act+0x5D82)` = Exhaust 蓄积计数**，`+0x5D88` = 衰减 timer。
阈值来自 `emNNN_00_dttune`（迅龙 180/75/480 [C]）。
`0x5D82` 是**硬编码立即数 ⇒ 跨怪通用**，符合本任务「不按单怪建规则」。

## 3 · v40 实现（v38 规则逐字节不变）

| 项 | 内容 |
|---|---|
| 一次性写入 | 第一次 `0xAFF40` 动作开始时，若 `c4 != 1`（非愤怒）、`FORCED==0`、`GATE_LIVE==1`、`heap_ok(actp)`，则 `write_volatile<u16>(actp+0x5D82, 1000)`；`FORCED=1` 熔断，全场最多一次 |
| 写入值 1000 | 高于所有已知怪的 `max`（≤850），walker 会钳到 max，仍 ≥ `initial`（最高 300）⇒ 下一次动作必定触发疲惫 |
| `F` 行 | 记录写入事件（帧 / mon / act / 写入前后 ex / 当时 c4） |
| `C` 行 | **`forge_onUpdate` 每帧**读缓存 mon 的 `+0xCAC4`，值一变立即打日志，上限 400 条 —— **不受 A 行 1/4 采样限制** |
| A 行 | 保留 `c4/cf/e1/dc/h1`，新增 `ex`（写入后实际蓄积值）、`forced` |
| 规则 | v38 prev 表 2 项 + 剩余权重归一化重抽，**完全不变** |
| 兼容 | banner 保留 "RAI v39" / "RAI v38" 串 ⇒ `analyze_v39_state.py` 与 `analyze_v38_log.py` 均可直接跑 |

**为什么 C 行是关键**：P10 日志里 A 行是「每 4 个动作开始 1 条」，而怪物
疲惫时流口水/喘气/倒地、几乎不出招 ⇒ A 行会**系统性跳过整个疲惫段**。
这是上一轮「用户看到了疲劳、日志却没抓到」的真正原因，比「疲劳没发生」
更可能。C 行每帧监控把这个问题彻底消除。

## 5 · 一轮实机判据

双击 `8_lite_check.bat` → 进任意任务 → 锁定 → 站着 60 秒 → 正常关游戏，
脚本自动出 `lite_result.txt`（v38 规则判据）+ `lite_state_result.txt`（状态判读）。

判读脚本 `tools/analyze_v39_state.py` 已升级：解析 `F` / `C` 行、
输出 C 行状态段与 `c4==2` 段时长、A 行 `ex` 分布、V 行按状态分组，
并在结论里检查「写入 → c4==2」全链路。旧日志冒烟 SKIP 通过，
模拟 v40 日志判读 PASS（能正确识别 F 行与 c4==2 段）。

**判据**：零 FATAL / `F` 行恰好 1 条 / C 行出现 `c4==2` 段 / A 行 `ex` 在写入后
呈衰减或钳制形态 / `live=1` / 用户体感无反复疲惫或动画错位。
用户只需补一句「怪物大概在哪个时刻变疲劳」，与 C 行段对照即可定案。
