# P50 · v56 动作耐力消耗 ×64：1~2 个动作自然疲惫（2026-11-14 15:55，已部署未实机）

## 0 · 需求与方案选择

用户 15:55：「下场继续打雄火龙，能不能修改掉雄火龙动作的消耗耐力值，
让其在一两个动作后疲劳。这样也能验证链路。」

**选了「改传入参数」，没改 arc 数据表**，理由：

| 路径 | 做法 | 代价 | 判定 |
|---|---|---|---|
| **A（本版）** | 在已装的 `h_stamina @0xBD260` 里把每次负 `delta` ×64 | 零新增 hook、零写入、跨怪通用、不读 action_id | ✅ 采用 |
| B | 定位 `0x756A8 bl 0x711E8` 查的 (动作id, sub) 消耗表，改表值后单条目重封 arc | 需定位表所在 arc + 每怪一份 + 触碰游戏资源；项目纪律禁止整包重封大 arc | ❌ 成本高、跨怪不通用、偏离「验证链路」目的 |

A 改的是**游戏查表后传给 `0xBD260` 的那次消耗值**，对状态机而言与「数据表里
写了更大的消耗」等价；且能直接在日志里看到 `原始 d0 → 放大 d1`，验证价值更高。

## 1 · 数值依据（全部来自 P49 实机）

- P49 G 行 `d0=4294967288` = **−8** ⇒ 雄火龙该动作原始耐力消耗 8 点
- `act+0x508` 当前耐力初值 800（本场）/ 上限 `t506=1000`
- `0xBD2AC rsb r3,delta,#0` / `0xBD2B4 cmp cur,r3` / `0xBD2B8 ble 0xBD350`
  ⇒ 当 `cur <= -delta` 时游戏自己走耗尽分支

`DRAIN_MUL = 64` ⇒ −8 × 64 = **−512**：

| 初始 cur | 第 1 次动作 | 第 2 次动作 |
|---|---|---|
| 800 | 800 > 512，不耗尽，写回 **288** | 288 <= 512 ⇒ **耗尽分支** |
| 1000 | 1000 > 512，不耗尽，写回 **488** | 488 <= 512 ⇒ **耗尽分支** |

若某动作原始消耗更大（−16 → −1024），第 1 次即耗尽。
⇒ **1~2 个动作**，符合用户要求。

耗尽后由游戏原生链路继续（P49 已全链路实证）：
`+0x508=0 → +0x505=1 → 0x76154 门控 1→2 → 0x816D0 → 0xF8D384
→ Stamina_low_Start → +0x50C 计时器约 4800 帧 → 2→3→0 → t508 恢复 800`。

## 2 · v56 相对 v55 的改动

| # | 改动 |
|---|---|
| 1 | `h_stamina` 由「一次性 `delta=-(cur+1)`」改为「**每次负 delta 乘 `DRAIN_MUL=64`**」（`saturating_mul` + `max(-8000)` 防溢出）。只放大 `(a1 as i32)<0` 的扣减调用，不碰恢复/其它调用 |
| 2 | 新增 **`DRAIN_DONE` 熔断**：一旦游戏自己推进到疲惫（`a505>=1 \|\| a508==0`）即停止放大，之后完全原样透传 ⇒ **只产生一个疲惫窗口**，不会在疲惫结束后反复触发 |
| 3 | 新增 **J 行**（配额 40）：每次放大记录 `d0/d1/cur/a505/a508/an/jn`，可直接数出「几个动作扣光」 |
| 4 | G 行仍只在耗尽那次输出 **1 条**，新增 `jn=` 累计放大次数；S 行 `gdone/gf` 保留 |

**不变**：6 个 hook 点位/数量（复用已装 `h_stamina`，零新增）、零游戏内存写入、
W 行链 I 全字段、W1 疲惫判据读 `act+0x505`、v53 分段配额、所有门控
（`LOW==0` / `f>=1800` / `A_N>=20` / 目标怪 `ST_AN>=4` / `0<thr<0x4000` /
`+0x505==0` / `heap_ok` / `GATE_LIVE`）、`original!` 除一次性 delta 外参数透传。

**跨怪通用**：不读 action_id、不硬编码怪种数值；倍率作用于游戏查表得到的 delta，
对任何怪的任何动作都成立。门控里 `thr` 合法会排除小怪（thr=65535）。

## 4 · 下场看什么（雄火龙）

双击 `8_lite_check.bat`，正常打。放大在 **约 30 秒 / 全场 20 次动作后**开始，
随后 **1~2 个怪的动作**内应可见疲惫；看到后继续打到疲惫结束（约 80 秒）再正常关游戏。

第二份报告会直接打印：

```
=== v56 动作耐力消耗逐次轨迹 ===
  J f=... d0=... d1=... cur=... -> a505=... a508=... jn=1
  J f=... d0=... d1=... cur=... -> a505=1 a508=0   jn=2
  原始消耗 d0=-8，放大后 d1=-512（倍数 64.0）
  => 2 个动作后游戏自己判定耗尽
```

验收判据：
- `J` 行 1~3 条、`d0→d1` 倍数 64、末次 `a505>=1 / a508=0`
- `G` 行 1 条且 `jn == J 行数`
- W 行 `t505` 走 `0→1→2→3→0`、`t50c` 计时器斜率 −1/帧
- `st3=2 / wm=3 / wt>0`（W1 疲惫形状）
- 零 FATAL、零 `c0000005`、`live=1`、无观测盲区

## 5 · 边界

1. **尚未实机**。`DRAIN_MUL=64` 是按 P49 实测 −8 与 cur 800/1000 推的；
   若下场首个被放大的动作消耗不同，可能 1 个动作就耗尽（符合预期）或需要略多。
2. **不是改 arc 数据表**：改的是 `0xBD260` 的入参。要真正改资源表需走方案 B。
3. `DRAIN_DONE` 是全局熔断：若场上同时有多只大怪，第一只疲惫后其它怪不再放大。
   本场只打雄火龙，无影响。
4. 只放大**负数** delta；`0xBD260` 的正 delta（恢复）调用原样透传，
   所以疲惫结束后的耐力恢复不受干扰。
5. `f>=1800 / A_N>=20` 门控保留 ⇒ 「1~2 个动作」是从约 30 秒之后算起，
   不是任务刚开始。
6. P33 的 `c0000005` 仍未归因；v55 实机零异常。

## 6 · 用途

这版把 P49 的「一次性跳过累积」换成「**多次真实扣减 → 累积到 0 → 游戏自己判定耗尽**」，
能验证链 I 的每动作扣减环节确实在跑（而不只是验证了耗尽分支），
并顺带复验 `+0x505` 四态、`+0x50C` 计时器与 W1 疲惫形状在放大消耗下是否一致。
若下场这些字段与 P49 完全一致 ⇒ 「强制/放大不引入偏离原版的行为」得到强证据，
之后可放心推进 P49 §7 的 **W2 距离档**。
