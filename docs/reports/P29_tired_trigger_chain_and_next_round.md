## 2 · 本地链路：疲惫如何触发（字节级 [C]）

数据源：
`00_Tools/92_MHGU-master/MHGU-master/docs/reference/re-example-dttune-consumer.md`
（§2 loader / §3 内存布局 / §4 消费链 / §8 交接表）
+ `04_RiseAI/refs/hpbar/main_text_decomp.bin` ARM A32 反汇编。

### 2.1 数据层 → 运行期

- `dttune` 资源挂在 `em+0x75EC`，getter `0x71078 = *(em+0x75EC) + 0x64`。
  状态块按 `[getter+0x34..0x54]` = `res+0x98..0xB8` 排列，每块 12 B：
  `u16 [initial, A, B, durF, increase, max]`。
- 160 个 `bl 0x71078` 调用点按块偏移分组；**`[getter+0x44] = res+0xA8`
  = Exhaust（减气/疲惫）块**，5 个专属调用点。
- `act = *(em+0x1428)`（我们一直用的对象）。减气专属运行期字段：

| act+ | 类型 | 语义 | 日志字段 |
|---|---|---|---|
| `0x5D82` | u16 | **counter 蓄积** | `ex` |
| `0x5D84` | s16 | **当前阈值 thr** | 新增 `thr` |
| `0x5D88` | f32 | 衰减计时器（B/A 周期扣点） | `d5`（旧读低 16 位） |
| `0x5D8C` | u8 | **已触发次数 proc** | 新增 `proc` |
| `0x4D8` | s16 | **本次动作减气点数 amount** | 新增 `amt` |
| `0x5E08` | u8 | 状态**位**（毒/眠/麻/气绝…） | 新增 `flg` |
| `0x5E0C` | f32 | 时长计时器（`durF`） | 新增 `t5c` |

`act+0x5E08` 各位由 `[getter+0x38/0x40/...]` 的 proc-after 置位：
`bit0=0x01`（睡眠 0xA28BC）、`bit1=0x02`、`bit2=0x04`、`bit3=0x08`、
`bit4=0x10`（气绝/眩晕 0xA2F0C / add 0xA2E18 检查 `& 0x10`）。
**减气 add 0xA30E4 完全不检查 `0x5E08`** ⇒ 减气是瞬时判定、无固定时长
（`wiki/monster-status.md` 的「骑乘/减气/跳跃/爆破是瞬时判定」），
这正是「找不到状态字」的根因。

### 2.2 消耗 → 判定 → 状态切换（本轮新反汇编）

```
0x9DB54 (+5 callers, per-monster 0x172044/0x173894/...)
    └ 0x9DBE4: ldrh r1,[act+0x4D8]; add r1,r1,r3; strh   ← 每动作累加 amount
0x98A60 → 0x9A34C（每帧/每动作状态更新总入口）
    ├ 0x9A3A8: amount=act+0x4C8 → bl 0xA27C8 (睡眠块 add)
    ├ 0x9A424: amount=act+0x4D2 → bl 0xA2E18 (气绝块 add)
    ├ 0x9A470: amount=act+0x4D8 → bl 0xA30E4 (EXHAUST add)  ★
    └ ... 0x4DA/0x4DC/0x4CE → 其他状态块
0xA30E4 EXH add(em, amount):
    r8 = thr (ldrsh [act+0x5D84])
    counter (act+0x5D82) += amount; 若 amount>=1 重置衰减计时器 act+0x5D88
    r0 = blx [vt+0x39C]   ← 状态抑制查询
    if r0 != 1 && counter >= thr: counter = thr; return 1   ★ 触发
    if r0 == 1 && counter >= thr: counter = thr-1; return 0 ← 抑制
0x9A474 判定返回 1 → 0x80AF8（效果/通知）
0x75F0C → 0xA3198 EXH grow:
    counter = 0 ; proc (act+0x5D8C) + 1 (cap 30)
    thr = min(initial + increase*proc, max)   ← 再乘 k=f32[sb+0x10]
    tail b 0xA4130 → ldr r3,[vt+0x1CC]; mov r1,#9; bx r3
        → Stamina_low_Start / tired_start / tired_Loop（P20 的 FSM 状态名）
```

### 2.3 与实机的数值闭环

- `grow` 的 `initial + increase×proc` 正是 P24 观察到的 **30 / 80 / 130 / 180**
  （`em085_00_dttune @+0x2EC = (30,600,5,0,50,350)`，increase=50，cap max=350）。
  P24 `ex` 停 80、P25 停 120 都未越过对应阈值 ⇒ 未触发，完全自洽。
- P19 原版 `initial=150`，主怪 `ex` 5→150 后停止出招并流口水 ⇒ 触发点。
- P22 改 30 后 1:40 触发、2:40 恢复 ⇒ 触发条件与结束条件分离：
  **结束靠进食/耐力回升，不是 `durF` 计时器**（`durF` 对减气无效）。
- Rise 侧对应：Rise `ActionInfo._subStaminaPoint`（em002 393 动作中 98 个非零、
  5~50 点）就是这里的 `act+0x4D8`；`EnemyStaminaData._tiredSec` 与
  `Stamina_low_Start` 状态名同构（P20 报告）。

### 2.4 为什么此前 28 轮全败（一句话）

一直在改「累加通道的结果」（写 counter）、「不走的静态函数」或「结果的标志」，
而**疲惫根本没有持续状态字节**：它是 `add` 里 `counter >= thr` 的一次瞬时事件，
由游戏自己通过虚表通知 FSM。写 counter 不跑 `+=` 路径，写状态字找错了对象。

## 3 · 下一轮：v48 已部署（`f4c6d2b7…`，40960 B）

游戏已关闭、临时 mod 已回退、基线干净（`load_order` 无追加、无 arc 覆盖、
`6_` md5 `7361445f…` 未动、插件目录 md5 与产物一致）。

### 3.1 v48 做什么

1. **hook `0xA30E4`（EXH add）**：运行时首字必须是 `E92Dxxxx` push 家族
   （排除 IPS32 `E28FFxxx` 跳板），否则 `SKIP h_exh`、保持纯只读。
   静态首字 `E92D41F0` [C]。
2. **一次性有界强制**：首次满足 `f>=600 && A_N>=20 && GATE_LIVE &&
   0<thr<0x4000` 时，把 `amount` 放大为 `thr+16`，其余调用原样透传，
   `original!` 恒调用。⇒ 由**游戏自己**的 `add` 判定成立并走完整状态机，
   不写 counter、不写状态字、不写参数表、不碰 action_id（跨怪通用）。
   一次性熔断 `EXH_FORCED`，不会反复疲惫。
3. **纯只读观测**：`U` 行记录每次 EXH add 调用与强制前后字段；
   `R` 行改为**无条件定时快照**（修 P27/P28 盲区），新增
   `thr/proc/amt/flg/t5c/s3f/f5c`；`C` 行指纹纳入 `flg/proc/thr`；
   `MAX_R 900→1800`、`MAXLOG 2400→4200`。
4. **v38 AI 规则逐字节不变**；`hub=15` 保持兼容。
5. 回退：`out/rai_tired_snapshot_v47.nro`（`0fd173bd…`，纯只读）覆盖插件 nro。

### 3.2 判据（自动出在第二份报告）

`INSTALL h_exh`（而非 SKIP） / `U` 行恰好 1 条 `force=1` 且 `amt=thr+16` /
`POST ret=1` / 触发后 `proc` 递增且 `counter` 归零 /
`R` 行 `thr` 按 `initial+increase×proc` 递推 / 窗口内出现新值字段 /
零 FATAL / `live=1`。模拟日志 **PASS=11 / FAIL=0**，v47 真实日志降级不崩溃。

### 3.3 操作（用户负担最小）

双击 `8_lite_check.bat` → 任意任务（跳狗龙王是已验证短场）→ 正常打约 20 个
怪物动作 → 看是否很快流口水/喘气/动作变慢 → **立即正常关游戏**
（别久留任务状况菜单）→ 自动出两份报告，第二份是 v48 判读。
只需告知「是否很快疲劳、大概何时」及有无异常。

### 3.4 风险与边界

- 新增 1 个 hook + 改 1 次调用参数，属**游戏侧行为改动**（比纯只读高一档）。
  异常（闪退/冻结/反复疲惫/动画错位）立即退出并回退 v47。
- `0xA30E4` 的 `[vt+0x39C]()` 若返回 1 会抑制触发（add 返回 0），
  此时 `U` 行 `ret=0` 会如实记录，插件不会重试。
- `0xA30E4` 静态首字已核对，但**运行时首字**受 IPS32 变体影响 [U]；
  首字不符即自动 SKIP，本轮退化为纯只读观测（仍可拿 `thr/proc/amt` 数据）。
- `amount` 放大到 `thr+16` 上限 < 0x4000，保证不溢出 u16 counter。
- 若触发成功，下一步即可回 AI 主线 **3 状态权重层**：
  怒 `st==1`、疲惫用「`proc` 递增事件 + BEAT 频次下降」行为判据、
  普通其余；跨怪通用、零写入、不硬编码任何怪种数值。
